# 코드 완료 후 자동 검증 및 리뷰 워크플로우

작성일: 2026-05-17

## 목적

코드 작성이 끝났다고 바로 완료로 보지 않는다. Codex는 구현이 끝난 뒤, 계획한 태스크가 실제로 모두 반영되었는지, 사용자가 기대한 기능이 동작하는지, 누락된 태스크나 회귀가 없는지 확인한 뒤에만 완료를 보고한다.

이 문서는 코드 완료 직후 자동으로 반복할 검증과 리뷰 기준이다.

## 자동 실행 기준

다음 상황에서는 항상 이 워크플로우를 실행한다.

- 새 기능, 화면, API, 데이터 모델, 권한, 운영 플로우 구현이 끝났을 때
- 버그 수정이 끝났고 "정말 고쳐졌는지" 확인해야 할 때
- 사용자가 "코드 완료", "리뷰", "잘 동작하는지 확인", "빠진 태스크 확인"을 요청했을 때
- PR 작성, 커밋, 배포, 머지 전 최종 확인이 필요할 때

문서나 포맷만 바꾼 경우에는 관련 없는 브라우저 검증을 생략해도 된다. 대신 변경된 문서의 링크, 용어, 명령어, 날짜, 경로가 맞는지는 확인한다.

## 입력으로 확인할 것

리뷰를 시작하기 전에 다음 자료를 모은다.

- 사용자 요청 원문과 최신 추가 요청
- 관련 계획 문서 또는 체크리스트
- 현재 브랜치와 `git status --short`
- `git diff --stat`과 변경 파일 목록
- 새로 추가되거나 변경된 테스트
- 실행 가능한 검증 명령과 필요한 환경변수

계획 문서가 있으면 태스크 목록을 기준으로 삼는다. 계획 문서가 없으면 사용자 요청과 변경 diff를 기준으로 임시 태스크 목록을 만든다.

## 자동 리뷰 순서

### 1. 변경 범위 고정

먼저 현재 변경 파일을 확인하고, 이번 요청과 무관한 변경은 리뷰 범위 밖으로 분리한다.

확인할 것:

- 현재 브랜치가 `main`이 아닌지
- 예상하지 못한 파일이 섞이지 않았는지
- 기존 사용자 변경을 되돌리거나 덮어쓰지 않았는지
- 새 파일, 삭제 파일, 설정 파일 변경이 의도된 것인지

### 2. 태스크 커버리지 매트릭스 작성

계획 또는 사용자 요청을 기준으로 태스크별 완료 상태를 확인한다.

권장 형식:

```markdown
| 태스크 | 구현 위치 | 완료 기준 | 검증 방법              | 상태                 |
| ------ | --------- | --------- | ---------------------- | -------------------- |
| ...    | `src/...` | ...       | `npm test` / 수동 확인 | 통과 / 미흡 / 미확인 |
```

상태 기준:

- `통과`: 코드와 검증 결과가 완료 기준을 만족한다.
- `미흡`: 일부 구현됐지만 요구사항 또는 UX가 부족하다.
- `미확인`: 코드상 구현은 보이나 실제 동작 검증을 못 했다.
- `누락`: 태스크가 diff에 반영되지 않았다.

`미흡`, `미확인`, `누락`이 있으면 완료로 보고하지 않고 후속 작업을 먼저 제안하거나 직접 수정한다.

### 3. 자동 검증 실행

기본 검증은 프로젝트 스크립트에 맞춘다.

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

UI 또는 사용자 흐름이 바뀌면 가능한 경우 추가로 실행한다.

```bash
npm run test:e2e
```

검증 결과를 요약할 때는 성공 여부만 쓰지 말고, 실패한 명령이 있다면 실패한 테스트 이름, 에러 요지, 영향 범위를 함께 적는다.

### 4. 실제 동작 확인

테스트가 통과해도 핵심 사용자 흐름은 한 번 더 확인한다.

UI 변경이면 다음을 확인한다.

- 첫 화면에서 주요 액션이 보이는지
- 모바일과 데스크톱에서 레이아웃이 깨지지 않는지
- 로딩, 빈 상태, 에러 상태가 어색하지 않은지
- 버튼, 폼, 지도, 목록, 모달 같은 주요 인터랙션이 실제로 반응하는지

API 또는 서버 변경이면 다음을 확인한다.

- 성공 응답과 실패 응답이 모두 의도한 status code와 body를 반환하는지
- 인증, 권한, 환경변수 누락, 외부 API 실패가 안전하게 처리되는지
- 운영에서 개발용 fallback이 조용히 사용되지 않는지

데이터 변경이면 다음을 확인한다.

- migration 또는 schema 변경이 기존 데이터와 충돌하지 않는지
- RLS, Storage policy, owner check가 의도한 범위를 넘지 않는지
- 삭제, 숨김, 신고, 수정 같은 상태 전환이 되돌릴 수 있거나 관찰 가능한지

### 5. 빠진 태스크와 회귀 찾기

다음 관점으로 누락을 찾는다.

- 계획 문서의 모든 하위 태스크가 diff에 반영됐는가
- 새 UI 상태를 추가했는데 테스트 또는 수동 확인이 없는가
- 새 API를 추가했는데 실패 케이스 테스트가 없는가
- 도메인 타입을 바꿨는데 import/export 또는 public API가 갱신됐는가
- 운영 문서, `.env.example`, README, PR 설명에 반영해야 할 변화가 있는가
- `TODO`, `FIXME`, `skip`, `only`가 남아 있지 않은가
- 기존 핵심 흐름을 우연히 깨뜨릴 수 있는 변경이 있는가

### 6. 코드 리뷰 관점 점검

최소한 다음 리뷰를 수행한다.

- 정확성: 요구사항과 구현이 일치하는가
- 안정성: 에러, 비동기, 외부 API 실패, 빈 데이터가 안전한가
- 보안: 인증, 권한, 입력값, secret, 개인정보가 안전한가
- 유지보수성: 기존 구조와 이름, 레이어 경계를 따른다
- 테스트: 핵심 성공/실패 경로를 충분히 검증한다
- 성능: 반복 호출, 큰 목록, 지도 렌더링, 네트워크 요청이 불필요하게 늘지 않았다

리스크가 큰 변경은 `review`, `qa`, `qa-only`, `design-review`, `cso` 같은 관련 gstack skill로 한 번 더 확인한다.

## 완료 보고 형식

완료 보고에는 다음을 포함한다.

```markdown
## 구현 완료 리뷰

### 태스크 커버리지

| 태스크 | 상태                        | 근거 |
| ------ | --------------------------- | ---- |
| ...    | 통과 / 미흡 / 미확인 / 누락 | ...  |

### 검증

- `npm run lint`: 통과 / 실패 / 미실행
- `npm run typecheck`: 통과 / 실패 / 미실행
- `npm test`: 통과 / 실패 / 미실행
- `npm run build`: 통과 / 실패 / 미실행
- `npm run test:e2e`: 통과 / 실패 / 미실행 / 해당 없음

### 실제 동작 확인

- 확인한 흐름:
- 확인하지 못한 흐름:
- 남은 리스크:

### 결론

- 완료 여부:
- 먼저 고쳐야 할 항목:
- 후속 태스크:
```

## 완료 판정

완료로 보고할 수 있는 조건:

- 모든 필수 태스크가 `통과` 상태다.
- 관련 자동 검증이 통과했거나, 미실행 이유가 명확하다.
- 핵심 사용자 흐름 또는 API 흐름을 실제로 확인했다.
- 남은 리스크가 사용자에게 명확히 공유됐다.
- 누락 태스크가 있으면 완료가 아니라 후속 작업으로 분리했다.

완료로 보고하면 안 되는 조건:

- 실패한 테스트가 있는데 원인과 영향 범위를 설명하지 않았다.
- 계획된 핵심 태스크가 diff에 없다.
- UI 변경이 있는데 렌더링이나 상호작용을 확인하지 않았다.
- API 또는 권한 변경이 있는데 실패/권한 케이스를 확인하지 않았다.
- 운영 환경에서 데이터 유실이나 잘못된 fallback 가능성이 남아 있다.

## Codex 실행 메모

코드 작성 후에는 아래 순서로 움직인다.

1. 최신 사용자 요청을 다시 읽는다.
2. `git status --short`와 변경 파일 목록을 확인한다.
3. 계획 문서나 요청 사항을 태스크 목록으로 바꾼다.
4. 태스크 커버리지 매트릭스를 만든다.
5. 필요한 자동 검증과 실제 동작 확인을 수행한다.
6. 미흡하거나 누락된 항목은 완료 보고 전에 수정한다.
7. 수정할 수 없는 항목은 이유, 영향, 후속 태스크를 명확히 적는다.

이 워크플로우는 사용자의 "완료" 요청을 늦추기 위한 절차가 아니라, 완료라는 말을 실제 상태와 맞추기 위한 안전장치다.
