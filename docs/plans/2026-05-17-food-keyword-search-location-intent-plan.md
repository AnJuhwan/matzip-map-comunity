# 네이버 음식 키워드 검색 위치 의도 개선 계획

작성일: 2026-05-17

Notion 계획: https://www.notion.so/363f1beebaaf81f8a978cd821fbd5af8

## 배경과 목표

현재 지도 검색은 입력 전체를 먼저 지오코딩한다. 그래서 `갈비` 같은 음식 키워드도 임의의 장소 좌표로 해석되면 지도가 이동한 뒤 후보가 나온다. 목표는 음식 키워드만 입력하면 현재 지도 화면 주변에서 찾고, `마곡갈비`처럼 지역과 음식이 붙은 입력은 지역 근처 음식점으로 해석하는 것이다.

## 범위와 제외 범위

- 범위: 검색어 의도 분리, 후보 API 쿼리 구성 개선, 후보 필터링 보완, Vitest 회귀 테스트 추가
- 제외 범위: 네이버 API 제공자 교체, UI 레이아웃 변경, Supabase 스키마 변경

## 하위 태스크

- 검색 의도 파서 추가
  - 수정 영역: `src/features/naver-place-import/model/nearby-place-candidates.ts`
  - 완료 조건: `갈비`는 현재 주변 음식 검색, `마곡갈비`는 지역+음식 검색으로 분류된다.
  - 검증: 모델 단위 테스트
- 클라이언트 검색 흐름 수정
  - 수정 영역: `src/widgets/matzip-community/model/use-matzip-community.ts`
  - 완료 조건: 음식 전용 검색은 지오코딩하지 않고 현재 bounds/areaQuery로 후보 API를 호출한다.
  - 검증: 훅 테스트
- 후보 API 쿼리 수정
  - 수정 영역: `src/app/api/nearby-place-candidates/route.ts`
  - 완료 조건: `query=갈비&areaQuery=마곡동`은 네이버에 `마곡동 갈비`로 요청한다.
  - 검증: API route 테스트
- 후보 필터링 보완
  - 수정 영역: `src/widgets/matzip-community/model/use-matzip-community.ts`
  - 완료 조건: `마곡갈비`와 `마곡 갈비`가 같은 검색으로 매칭된다.
  - 검증: 훅 또는 모델 테스트

## 구현 후보

1. 클라이언트에서만 지오코딩 여부를 막는다.
   - 장점: 변경 범위가 작다.
   - 단점: API가 여전히 `갈비` 단독으로 검색해 현재 지역성이 약하다.
2. 클라이언트와 API 양쪽에 검색 의도 정보를 반영한다.
   - 장점: 지도 이동 문제와 지역 검색 품질을 같이 개선한다.
   - 단점: 검색어 파서가 새로 생겨 테스트가 필요하다.
3. 좌표 기반 장소 검색 제공자를 새로 찾는다.
   - 장점: 네이버 지도 앱에 가장 가까운 경험을 만들 수 있다.
   - 단점: 외부 API 조사와 연동 범위가 커서 이번 수정에는 과하다.

## 선택한 방법

방법 2를 선택한다. 기존 `/api/nearby-place-candidates` 경로를 유지하면서, 사용자가 기대하는 두 흐름을 모두 보완할 수 있다.

## 영향

- 데이터: 저장 데이터 변경 없음
- API: 기존 파라미터를 유지하되 `query`와 `areaQuery`가 함께 들어올 때 검색어 조합이 달라진다.
- UI: 입력창과 목록 UI는 유지한다.
- 상태 관리: 검색 제출 시 지오코딩할지 여부가 의도별로 나뉜다.
- 권한과 보안: 인증/권한 변경 없음. 사용자 입력은 기존 sanitize와 길이 제한을 유지한다.

## 리뷰 결과

### CEO 리뷰

- 생각: 사용자가 지도에서 맛집을 찾는 핵심 기대와 직접 맞닿은 수정이다.
- 우려: 너무 많은 자연어 해석을 넣으면 예측 가능성이 떨어진다.
- 결정: 음식 키워드와 지역+음식 패턴만 좁게 처리한다.

### 디자이너 리뷰

- 생각: UI를 늘리지 않고 검색 결과의 행동만 사용자의 기대에 맞춘다.
- 우려: `마곡갈비` 같은 붙여쓰기 입력이 결과에서 사라지면 안 된다.
- 결정: 공백 무시 매칭을 추가한다.

### 개발자 리뷰

- 생각: 파서, 훅, API route에 각각 테스트를 두면 회귀를 잡기 쉽다.
- 우려: 네이버 Local Search 자체가 좌표 파라미터를 받지 않아 지역성은 areaQuery prefix와 bounds filter 조합에 의존한다.
- 결정: 현재 지도 areaQuery를 검색어에 붙이고 bounds 필터를 유지한다.

### 보안 이슈 리뷰

- 생각: 인증/권한 변경은 없고 사용자 입력 기반 외부 API 호출만 바뀐다.
- 우려: 긴 검색어 또는 이상한 공백 입력이 외부 API에 그대로 커질 수 있다.
- 결정: 기존 sanitize와 max length를 유지하고 새 파서는 trim/normalize만 사용한다.

## 최종 정리된 방향

- 이번 작업에서 할 것: 음식 전용 검색은 현재 지도 주변 검색, 지역+음식 검색은 지역으로 이동 후 음식 후보 검색
- 이번 작업에서 하지 않을 것: UI 개편, 네이버 API 제공자 변경, 데이터 모델 변경
- 선택한 구현 방법: 클라이언트 검색 의도 분기와 API 지역 prefix 조합
- 구현 순서: 실패 테스트 추가, 모델 파서 구현, 클라이언트 흐름 수정, API 쿼리 수정, 검증
- 검증 방법: 관련 Vitest, `npm run typecheck`, `npm run lint`
