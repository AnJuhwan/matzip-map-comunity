# 네이버 음식점 기반 리뷰 지도 계획 v2

작성일: 2026-05-17

기획 저장소: [코덱스 기획 창고](https://www.notion.so/363f1beebaaf804d808de2d9cf668c95)

Notion 계획 페이지: [네이버 음식점 기반 리뷰 지도 계획 v2](https://www.notion.so/363f1beebaaf81f49a86f2943b48879a)

> 사용자 승인 전까지 구현하지 않는다. 이 문서를 확인한 뒤 사용자가 "진행해"라고 말하면 코드 수정을 시작한다.

## 배경과 목표

프로젝트 방향을 다시 정리한다.

이 서비스는 자체 음식점 DB를 만드는 프로젝트가 아니다. 네이버 지도에 등록된 음식점을 기준으로 보여주고, 우리 서비스는 그 음식점에 대한 사용자 리뷰만 관리한다.

사용자는 지도를 보면서 네이버 음식점을 탐색하고, 특정 음식점에 들어가 우리 서비스의 리뷰를 남긴다. 지도 이동, 검색, 공유 URL 모두 네이버 음식점 탐색을 기준으로 동작한다.

## 핵심 사용자 시나리오

1. 사용자가 처음 지도 화면에 들어온다.
2. 검색창이 비어 있으면 현재 지도 화면 안의 네이버 음식점이 표시된다.
3. 사용자가 지도를 이동하면 새 지도 화면 안의 네이버 음식점으로 목록과 마커가 바뀐다.
4. 사용자가 `마곡역 음식점`을 검색하면 지도 중심이 마곡역으로 이동하고, 마곡역 주변 음식점이 표시된다.
5. URL이 `/?search=마곡역 음식점`이면 공유받은 사람도 같은 검색어 기준으로 지도와 음식점 목록을 본다.
6. 내 위치 마커는 검색과 지도 이동에 따라 바뀌지 않고, 실제 내 위치에 계속 남는다.
7. 음식점 상세에서는 네이버 음식점 정보와 사진을 보여주고, 우리 서비스의 리뷰만 작성/수정/삭제한다.

## 중요한 제약

네이버 Local Search API는 지도 bounds 안의 모든 음식점을 직접 반환하는 viewport search API가 아니다. 따라서 "네이버 지도에 보이는 모든 음식점"을 완전하게 보장하려면 네이버 플레이스 내부 API나 별도 계약 API가 필요할 수 있다.

이번 구현에서는 다음 원칙을 사용한다.

- 사용자 경험은 "현재 지도 화면의 네이버 음식점"으로 만든다.
- 내부 표현은 "네이버 검색 후보"로 제한한다.
- bounds key 중복 방지 로직을 유지하고, 필요하면 debounce를 추가한다.
- 네이버 음식점은 탐색과 리뷰 대상의 canonical source로 사용한다.
- 우리 DB에는 리뷰를 연결하기 위한 최소 음식점 snapshot만 저장한다.

사진도 같은 제약이 있다. 현재 사용할 수 있는 공개 검색 API는 음식점의 공식 네이버 플레이스 사진 전체를 보장하지 않는다. 우선 네이버 이미지 검색으로 관련 사진 여러 장을 가져오고, "네이버 등록 사진 전체" 수집은 공식 API 가능 여부를 확인한 뒤 별도 범위로 다룬다.

## 이번 작업의 범위

- 네이버 음식점을 지도/목록의 기본 데이터로 사용한다.
- 지도 bounds와 검색어를 기준으로 네이버 음식점을 가져온다.
- 검색어가 있으면 검색어로 위치를 찾고 지도 중심을 이동한다.
- `?search=` 공유 URL을 지원한다.
- 음식점 마커에 가게 이름, 우리 서비스 리뷰 개수, 별점 또는 평점 대체값을 표시한다.
- 내 위치 마커는 실제 사용자 위치에 유지한다.
- 네이버 후보에 여러 장의 이미지 URL을 붙일 수 있는 모델을 만든다.
- 리뷰 작성 시 네이버 음식점 snapshot을 최소 저장해 리뷰의 기준점을 만든다.

## 제외 범위

- 네이버 지도에 등록된 모든 음식점의 완전한 수집 보장
- 네이버 플레이스의 실제 별점, 방문자 리뷰 수, 블로그 리뷰 수 수집
- 네이버 공식 플레이스 사진 전체 수집
- 음식점 정보를 사용자가 직접 등록하는 새 플로우 확장
- 지도 클러스터링
- 장기 캐시/대량 크롤링/백그라운드 수집

- 검증:
  - 빈 검색어, 검색어 있음, bounds 필터 테스트를 추가한다.

## 구현 방법 후보

### 방법 A. 현재 구조를 확장해 네이버 후보를 primary map data로 사용

장점:

- 현재 API와 지도 이벤트 구조를 가장 적게 바꾼다.
- 네이버 key를 서버에 유지한다.
- 빠르게 검색 공유 URL과 지도 bounds 탐색을 붙일 수 있다.

단점:

- places 테이블이 여전히 남아 있어 이름과 역할이 혼동될 수 있다.
- 네이버 후보와 저장된 리뷰 target을 합치는 로직이 필요하다.

### 방법 B. DB를 `restaurants/reviews` 또는 `naver_places/reviews`로 재설계

장점:

- 도메인 의미가 가장 정확하다.
- "음식점은 네이버, 우리는 리뷰"라는 구조가 코드에 분명히 드러난다.

단점:

- 마이그레이션 범위가 크다.
- 기존 상세/등록/리뷰 플로우를 많이 바꿔야 한다.
- 이번 기능보다 리스크가 커진다.

### 방법 C. 네이버 음식점은 프론트 임시 데이터로만 두고 리뷰 작성 시마다 새 snapshot 저장

장점:

- 구현이 가장 빠르다.
- DB 변경이 거의 없다.

단점:

- 같은 네이버 음식점이 중복 저장될 수 있다.
- 리뷰 통계가 음식점 단위로 합쳐지지 않을 수 있다.
- 공유 URL과 상세 페이지 일관성이 약해진다.

## 선택한 방법

방법 A를 선택한다.

이번 단계에서는 현재 구조를 확장하되, 도메인 표현을 "네이버 음식점 리뷰 대상"으로 명확히 한다. 대규모 DB 재설계는 다음 단계로 미루고, 먼저 사용자가 보는 지도/검색/공유/리뷰 흐름을 바로잡는다.

## 데이터, API, UI 영향

### 데이터

- 네이버 음식점 식별을 위한 stable key가 필요하다.
- 기존 `places`는 음식점 원본 DB가 아니라 리뷰 대상 snapshot으로 해석한다.
- 사진은 `heroImageUrl` + `photoUrls` 형태가 필요하다.

### API

- `/api/nearby-place-candidates`는 검색어와 bounds를 모두 받는다.
- 이미지 검색 display 수를 늘려 여러 사진 후보를 반환한다.
- 검색어 길이, 좌표, bounds 검증이 필요하다.

### URL

- 홈 화면은 `searchParams`를 읽어 클라이언트에 전달한다.
- 검색 제출은 URL을 `/?search=${query}`로 동기화한다.
- 검색어 제거 시 URL도 기본 경로로 돌아간다.

### UI

- 검색창 placeholder는 "역, 동네, 음식점 검색"처럼 네이버 음식점 탐색에 맞춘다.
- 목록 헤더는 검색어 없음이면 "현재 지도 음식점", 검색어 있음이면 "`검색어` 주변 음식점"으로 표시한다.
- 등록 CTA는 음식점 직접 등록보다 "리뷰 쓰기" 중심으로 약화하거나 이동한다.

## 리뷰 결과

### CEO 리뷰

- 생각: 제품 정체성이 좋아졌다. 음식점 DB를 만들려는 서비스가 아니라 네이버 음식점 위의 리뷰 레이어가 되면 범위가 명확하다.
- 우려: "네이버의 모든 음식점" 약속은 API 한계와 충돌한다.
- 제안: 사용자에게는 지도 화면 음식점 탐색으로 보이게 하되, 내부에서는 네이버 검색 후보라는 한계를 인정한다.
- 결정: 이번 단계는 네이버 음식점 탐색 + 우리 리뷰 관리로 범위를 고정한다.

### 디자이너 리뷰

- 생각: 검색어 공유 URL과 지도 중심 이동은 지도 서비스다운 핵심 경험이다.
- 우려: 음식점 직접 등록 CTA가 계속 강하면 "리뷰만 관리"라는 방향과 충돌한다.
- 제안: 검색창과 지도 마커를 중심에 두고, 음식점 상세에서 리뷰 작성 행동을 강조한다.
- 결정: 첫 화면은 네이버 음식점 탐색, 상세 화면은 리뷰 작성으로 역할을 분리한다.

### 개발자 리뷰

- 생각: 현재 후보 API와 지도 bounds 이벤트를 확장하면 빠르게 갈 수 있다.
- 우려: search param, 지도 idle, 후보 로딩, 위치 요청이 동시에 움직여 race condition이 생길 수 있다.
- 제안: `candidateLoadIdRef`, bounds key 중복 방지, 필요 시 debounce를 유지한다. 검색어 초기화와 URL 동기화는 한 곳에서 관리한다.
- 결정: hook에서 `appliedQuery`, `visibleMapBounds`, `mapFocusLocation`, `userLocation`의 책임을 분리한다.

### 보안 이슈 리뷰

- 생각: 네이버 API key는 계속 서버 route 안에 있어야 한다.
- 우려: 공유 URL 검색어가 외부 API 호출로 이어지므로 길이 제한과 입력 정리가 필요하다.
- 제안: query는 trim, 최대 길이 제한, 좌표/bounds 검증을 거친다. 이미지 URL은 렌더링 시 attribute escaping과 safe background handling을 유지한다.
- 결정: 서버 입력 검증과 클라이언트 출력 escape를 구현 조건에 포함한다.

### DX 리뷰

- 생각: 로컬 개발자가 네이버 키 없이도 흐름을 이해할 수 있어야 한다.
- 우려: API 키가 없으면 지도는 뜨는데 후보가 없는 상황이 혼동될 수 있다.
- 제안: candidateMessage에 "네이버 검색 API 키 필요"를 유지하고 테스트는 fetch mock으로 충분히 작성한다.
- 결정: 새 환경변수는 추가하지 않고 기존 네이버 검색/지도 키를 사용한다.

## 최종 정리된 방향

- 이번 작업에서 할 것:
  - 네이버 음식점을 지도와 목록의 primary data로 사용
  - 지도 bounds 이동 시 음식점 후보 갱신
  - 검색어 입력 시 지도 중심 이동 및 주변 음식점 표시
  - `?search=` 공유 URL 지원
  - 네이버 관련 사진 여러 장 표시
  - 내 위치 마커 유지
  - 우리 서비스 리뷰 통계와 네이버 음식점 후보 결합

- 이번 작업에서 하지 않을 것:
  - 네이버 음식점 전체 수집 보장
  - 네이버 실제 별점/리뷰 수 수집
  - 공식 네이버 플레이스 사진 전체 수집
  - 대규모 DB rename 마이그레이션

- 선택한 구현 방법:
  - 현재 구조를 확장해 네이버 후보를 primary map data로 사용한다.

- 선택 이유:
  - 제품 방향을 반영하면서도 지금 코드 구조에서 가장 안전하게 구현할 수 있다.

## 구현 중 디버깅 기록

### 2026-05-17 네이버 지도 음식점 미표시

- 증상: 지도 화면에서 네이버 음식점 마커가 표시되지 않았다.
- 원인 1: 후보 API가 음식점 후보마다 네이버 이미지 검색을 즉시 호출해 지도 이동/초기 로딩 시 네이버 Search API 호출량이 과도하게 늘었다.
- 원인 2: 검색어가 없는 지도 화면은 지역명(`마곡동`)이 필요하지만, 서버 역지오코딩 키가 허용되지 않는 경우 `queryArea: null`이 되고 `음식점` 같은 광역 검색어를 bounds로 필터링해 0개가 됐다.
- 결정: 지도 후보 조회에서는 사진을 기본으로 가져오지 않고 `includePhotos=1`일 때만 이미지 검색을 수행한다.
- 결정: 실제 네이버 지도 화면에서는 JS geocoder로 지도 중심 지역명을 얻어 `areaQuery`로 후보 API에 전달한다.
- 결과: `areaQuery=마곡동`이 전달되면 마곡동 bounds 안의 네이버 음식점 후보가 반환된다.
- 검증: route/hook 테스트, 전체 단위 테스트, lint, typecheck, build, e2e를 실행한다.
