## 배경과 목표

리뷰 작성자가 이미지를 선택했을 때 저장 전에 바로 확인할 수 있고, 저장된 리뷰에서도 사진을 자연스럽게 탐색할 수 있게 한다. 사용자가 요청한 핵심은 업로드 미리보기, 크게 보기, 업로드된 리뷰 이미지 노출, 슬라이드 형태, `1/3` 같은 현재 위치 표시다.

## 범위

- 리뷰 작성/수정 폼에서 여러 이미지 선택과 미리보기 제공
- 리뷰 저장 데이터에 여러 이미지 URL 저장
- 리뷰 카드에서 이미지 슬라이드와 `현재/전체` 표시 제공
- 미리보기와 저장된 리뷰 이미지 모두 크게 보기 모달 제공
- 기존 단일 `image_url` 리뷰 데이터는 계속 보이도록 호환 처리
- 리뷰 리스트가 내부 스크롤 컨테이너를 만들지 않고 전체 페이지 스크롤을 사용하도록 변경
- 리뷰를 읽는 동안 가게 정보가 일정 지점부터 sticky로 유지되도록 상세 레이아웃 변경

## 제외 범위

- 장소 대표 사진 업로드 흐름 변경
- 이미지 편집, 크롭, 압축, 드래그 정렬
- Storage 객체 삭제 자동 정리
- 관리자 moderation 화면

## 구현 후보

### 후보 A: `reviews.image_urls text[]` 추가, 기존 `image_url` 병행 유지

현재 장소 사진이 `photo_urls text[]`를 쓰는 전례가 있어 리뷰에도 같은 배열 모델을 붙인다. 저장 시 첫 이미지는 `image_url`에도 넣어 기존 화면과 마이그레이션 안전성을 유지한다.

장점: 현재 구조와 가장 잘 맞고, UI 요구인 `1/3`을 자연스럽게 지원한다. 기존 단일 이미지 데이터도 쉽게 fallback 처리된다.

단점: 배열 컬럼이라 사진별 메타데이터, 정렬 변경, 삭제 감사 로그에는 약하다.

### 후보 B: 단일 `image_url` 유지, 리뷰 전체 사진을 슬라이드처럼 보여주기

데이터 변경 없이 리뷰 카드나 상세 영역에서 여러 리뷰의 단일 이미지를 모아 슬라이드로 보여준다.

장점: DB 변경이 없다.

단점: 사용자가 말한 업로드 미리보기와 `1/3`은 리뷰 한 건 안의 여러 이미지처럼 읽히므로 기대와 어긋난다.

### 후보 C: `review_photos` 별도 테이블 추가

사진을 별도 테이블로 분리해 순서, 소유자, 삭제 상태, 메타데이터를 관리한다.

장점: 장기 확장성과 감사 가능성이 좋다.

단점: MVP에는 과하고 로딩/저장/정책 범위가 커진다.

### 후보 D: 리뷰 리스트 내부 가상 스크롤 유지, sticky만 추가

현재 `VirtualReviewList`의 고정 높이와 내부 `overflow-y-auto`를 유지한 채 가게 정보만 sticky로 만든다.

장점: 리뷰가 매우 많을 때 DOM 개수를 줄일 수 있다.

단점: 사용자가 요청한 "전체 페이지의 스크롤"과 맞지 않고, sticky 기준이 내부 스크롤과 문서 스크롤로 갈라져 체감이 어색하다.

### 후보 E: 내부 가상 스크롤 제거, 상세 페이지를 가게 정보 + 리뷰 흐름으로 재배치

리뷰 리스트는 전체 DOM 흐름에 렌더링하고, 가게 정보 카드는 CSS `position: sticky`를 사용해 페이지 스크롤 기준으로 고정한다.

장점: 요청과 가장 직접적으로 맞고 구현이 단순하다. sticky 기준이 브라우저 기본 스크롤과 같아 모바일/데스크톱 확인도 쉽다.

단점: 리뷰가 아주 많아지면 가상화보다 렌더링 비용이 커질 수 있다. 현재 커뮤니티 규모와 리뷰 카드 밀도를 고려하면 감당 가능한 범위로 본다.

### 후보 F: window scroll 기반 가상화 직접 구현

문서 전체 스크롤을 유지하면서 `window.scrollY`와 카드 위치 측정을 이용해 가상화한다.

장점: 페이지 스크롤과 성능 최적화를 동시에 노릴 수 있다.

단점: 동적 이미지 높이와 리뷰 카드 높이가 섞여 측정 오차, 스크롤 점프, sticky 간섭 위험이 커진다. 이번 요구에는 과하다.

### 후보 G: 라이브러리 기반 window virtual scroll

내부 스크롤 컨테이너는 만들지 않고, `@tanstack/react-virtual`처럼 window scroll 기반 가상화를 지원하는 라이브러리를 추가해 리뷰 카드 렌더링만 줄인다.

장점: 사용자가 원하는 전체 페이지 스크롤을 유지하면서 리뷰가 많을 때 렌더링 비용을 줄일 수 있다. 직접 window virtualizer를 만드는 것보다 스크롤 측정과 overscan 처리가 안정적이다.

단점: 새 런타임 의존성이 추가된다. 이미지가 포함된 동적 높이 리뷰 카드에서는 추정 높이와 실제 높이 보정이 필요하므로 구현과 검증 범위가 단순 리스트보다 커진다.

## 선택한 접근

후보 A를 선택한다. 기존 `places.photo_urls`와 같은 단순 배열 모델을 리뷰에도 적용하면 요구사항을 가장 작게 만족하면서 기존 `image_url` 데이터를 깨지 않는다. 업로드 제한은 우선 리뷰당 최대 3장, 파일당 5MB, JPG/PNG/WebP/GIF로 계획한다. `1/3` 요청이 명확하므로 기본 최대치를 3장으로 잡되, 구현 중 상수로 분리해 추후 조정 가능하게 둔다.

2026-05-19 추가 변경 요청에는 후보 E를 기본 선택으로 둔다. 리뷰 리스트는 `VirtualReviewList`의 내부 스크롤 컨테이너를 제거하고 일반 페이지 흐름으로 렌더링한다. 가게 정보는 리뷰 영역과 같은 부모 그리드 안에 두고 `lg:sticky lg:top-4` 같은 CSS sticky를 우선 적용한다. 모바일에서는 전체 가게 카드가 화면을 과하게 차지하지 않도록 기본 문서 흐름을 유지하고, 필요하면 compact sticky 요약만 별도 적용한다.

사용자가 virtual scroll 유지 여부를 다시 확인해 달라고 했으므로 후보 G의 방향을 반영한다. 새 의존성은 추가하지 않고 현재 요구에 필요한 작은 window scroll virtualizer를 구현한다. 핵심 제약은 유지한다: 리뷰 리스트 자체가 별도 스크롤 컨테이너를 만들면 안 되고, document/window scroll을 기준으로 가상화해야 한다.

## 데이터, API, UI, 상태, 권한 영향

- 데이터: `reviews.image_urls text[] not null default '{}'` 추가, 기존 `image_url` 값을 배열로 backfill.
- 저장소 로직: `imageFiles?: File[]`를 받아 각 파일을 기존 Storage 경로 규칙으로 업로드하고, `image_urls`와 `image_url`을 함께 저장.
- 읽기 로직: `image_urls`가 있으면 우선 사용하고 없으면 기존 `image_url`을 단일 배열로 변환.
- UI: 파일 입력은 `multiple`을 사용하고 선택된 이미지 URL을 object URL로 만들어 미리보기한다. 슬라이더에는 이전/다음 아이콘 버튼, `1/N` 배지, 크게 보기 버튼을 둔다.
- UI: 리뷰 리스트는 내부 고정 높이/컨테이너 스크롤을 제거하고 페이지 흐름에 쌓는다. 성능상 필요하면 window scroll 기반 virtualizer 라이브러리를 사용하되, 리뷰 영역 내부에 별도 스크롤 포트를 만들지 않는다. 상세 화면은 가게 정보와 리뷰 리스트를 분리해 데스크톱에서 가게 정보가 sticky로 따라오도록 한다.
- 권한/보안: RLS는 기존 reviews row 권한을 유지한다. Storage 업로드 정책은 owner folder 제한과 mime/extension 제한을 그대로 사용한다. 클라이언트 검증은 파일별로 수행한다.

## 리뷰 결과

### CEO 리뷰

- 생각: 리뷰 사진은 맛집 신뢰와 탐색 매력을 바로 올리는 기능이라 현재 제품 단계에 맞다.
- 우려: 이미지 편집이나 갤러리 관리까지 넓히면 핵심 흐름이 늦어진다.
- 제안: 이번에는 작성/조회 경험만 완성하고 관리 고도화는 미룬다.
- 결정: 미리보기, 저장, 카드 노출, 확대 보기만 포함한다.

### 디자이너 리뷰

- 생각: 미리보기와 저장된 리뷰의 탐색 패턴을 같게 하면 사용자가 학습할 UI가 줄어든다.
- 우려: 리뷰 카드 안 이미지가 텍스트 정보를 밀어내거나 모바일에서 버튼이 겹칠 수 있다. 추가 요청 기준으로는 sticky 가게 정보가 리뷰 본문을 가리거나 화면을 답답하게 만들 수 있다.
- 제안: 고정 aspect ratio, 작은 아이콘 버튼, `1/N` 배지, 모달 확대 보기로 밀도를 제어한다. sticky는 데스크톱에서는 전체 가게 정보 카드, 모바일에서는 기본 흐름 또는 얇은 요약형만 사용한다.
- 결정: 카드에는 적당한 높이의 이미지 영역을 두고 큰 감상은 모달에서 처리한다. 리뷰 리스트는 페이지 스크롤로 읽게 하고 가게 정보는 리뷰 독해를 돕는 위치에 sticky로 둔다.

### 개발자 리뷰

- 생각: 배열 컬럼은 현재 코드의 장소 사진 모델과 잘 맞고 마이그레이션도 작다.
- 우려: `image_url`과 `image_urls` 병행 중 불일치가 생길 수 있다. 추가 요청 기준으로는 내부 가상 스크롤 제거 뒤 대량 리뷰 렌더링 비용이 늘 수 있다.
- 제안: 저장 시 첫 이미지를 `image_url`에 동기화하고 읽기에서는 `image_urls` 우선 fallback 규칙을 고정한다. 리뷰 수가 커지기 전까지는 일반 리스트로 단순화하고, 성능 문제가 실제로 보이면 window scroll 기반 virtualizer 라이브러리를 사용한다.
- 결정: 도메인 타입은 `imageUrls?: string[]`를 추가하고 `imageUrl`은 호환 필드로 유지한다. `VirtualReviewList`의 내부 스크롤 포트는 제거한다. 라이브러리를 쓰더라도 document/window scroll 기준으로만 쓴다.

### 보안 이슈 리뷰

- 생각: 업로드 표면이 넓어지므로 파일 수, 타입, 크기 검증이 핵심이다.
- 우려: SVG, 과대 파일, owner 폴더 우회, 공개 URL 노출이 리스크다.
- 제안: 기존 `validatePhotoFile`을 파일별로 재사용하고 최대 3장 제한을 둔다.
- 결정: 새로운 Storage 정책은 만들지 않고 기존 bucket 정책 안에서 검증과 경로 생성을 강화한다.

### DX 리뷰

- 생각: 개발자용 API나 스크립트 변경은 없다.
- 결정: 별도 DX 리뷰는 생략하고 schema/migration/test 문서성만 유지한다.

## 최종 정리된 방향

- 이번 작업에서 할 것: 리뷰당 최대 3장 업로드, 미리보기, 리뷰 카드 슬라이드, 확대 모달, 기존 단일 이미지 fallback
- 추가 요청에서 할 것: 리뷰 리스트 내부 스크롤 제거, 전체 페이지 스크롤 사용, 가게 정보 sticky 배치
- 이번 작업에서 하지 않을 것: 이미지 편집, 정렬 변경, Storage 객체 삭제 자동화, 관리자 기능
- 선택한 구현 방법: `reviews.image_urls text[]` 추가와 `image_url` 호환 유지, 리뷰 목록은 전체 페이지 스크롤 기준 window virtualizer 렌더링, 가게 정보는 CSS sticky 사용.
- 선택 이유: 현재 `places.photo_urls` 패턴과 맞고, 추가 레이아웃 요청도 현재 컴포넌트 구조에서 작고 명확하게 반영할 수 있다. 사용자가 금지한 내부 리뷰 스크롤 컨테이너를 만들지 않으면서 긴 리뷰 목록 렌더링 비용도 줄인다.
- 구현 순서: 저장소 테스트 작성, migration/schema/domain 확장, 폼 상태 확장, 슬라이더/모달 UI 추가, 리뷰 카드 연결, 리뷰 리스트 내부 스크롤 제거 또는 window virtualizer 적용, 가게 정보 sticky 레이아웃 적용, 브라우저 검증
- 검증 방법: Vitest, lint, typecheck, build, 가능한 e2e와 수동 브라우저 확인. 추가 레이아웃은 데스크톱/모바일에서 window scroll, sticky 위치, 리뷰 카드 겹침 여부를 확인한다.

## 테스트와 검증

- TDD 순서로 저장소 테스트부터 작성한다: `image_urls` mapping fallback, 여러 파일 업로드 payload, 기존 단일 이미지 호환.
- UI 테스트 또는 e2e로 리뷰 폼 파일 선택 후 미리보기와 `1/N` 표시를 확인한다.
- 수동 브라우저 확인으로 리뷰 카드 슬라이드, 크게 보기, 모바일/데스크톱 겹침 여부를 확인한다.
- 리뷰 리스트가 내부 스크롤 컨테이너를 만들지 않고 전체 페이지 스크롤로 움직이는지 확인한다.
- virtualizer 라이브러리를 쓰는 경우에도 내부 스크롤 포트가 생기지 않고 document/window scroll 기준으로 동작하는지 확인한다.
- 가게 정보가 리뷰 스크롤 중 지정 top offset에서 sticky로 유지되는지 확인한다.
- 최종 게이트는 `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`, 가능하면 `npm run test:e2e`.

## 배포, 롤백, 관찰

- 배포 전 Supabase migration 적용 필요.
- 롤백은 UI가 `image_url` fallback을 유지하므로 새 컬럼 사용을 중단해도 기존 단일 이미지는 계속 표시된다.
- 관찰 포인트는 업로드 실패 메시지, 리뷰 저장 실패율, 모바일 이미지 영역 레이아웃이다.
